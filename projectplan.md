## 1. Project overview

DevStash is a personal developer resource management application where developers can save, organize, search, and revisit useful programming resources in one place.

Instead of having documentation, GitHub repositories, tutorials, and development tools scattered across browser bookmarks, DevStash provides a centralized library organized by technology, category, tags, and collections.

## 3. Feature scope

To avoid overengineering, we'll split the project into an achievable MVP and optional enhancements.

### MVP — Required features

Version 1.0

Authentication and profile

- Google Sign-In and Sign-Out
- Protected dashboard routes
- Google profile name, email, and avatar
- Private, user-specific bookmarks

Bookmark management

- Create, view, edit, and delete bookmarks
- Title, URL, description, technology, category, and tags
- Mark and unmark favorites
- Open saved links in a new tab
- Duplicate URL warning within a user's library
- Created and updated timestamps

Organization and discovery

- Predefined resource categories
- Custom tags
- User-created collections
- Assign bookmarks to multiple collections
- Search by title, URL, description, or tag
- Filter by technology, category, and favorites
- Sort by newest, oldest, and alphabetical order

Interface

- Dashboard with bookmark counts and recent resources
- Grid and list views
- Real technology icons
- Light and dark mode
- Mobile-responsive navigation
- Empty states, skeleton loading, toast notifications
- Confirmation dialogs for destructive actions

### Optional enhancements

Version 1.1+

- Automatic URL title and description extraction
- JSON bookmark import/export
- Keyboard shortcuts and command palette
- Public, read-only shareable collections
- Browser extension for saving current tabs
- Broken-link checking
- Usage insights and frequently accessed resources

For the first release, bookmarks will use manually entered metadata. This avoids scraping complexity, unreliable previews, and unnecessary security risks.

| Layer              | Responsibility                     |
| ------------------ | ---------------------------------- |
| UI components      | Display data and collect input     |
| Route Handlers     | Expose REST endpoints              |
| Validation schemas | Validate incoming data             |
| Services           | Business logic and ownership rules |

### Database rules and constraints

- Every bookmark belongs to exactly one user.
- Each bookmark can have zero or one primary technology.
- A bookmark can have multiple tags and belong to multiple collections.
- Technology records are globally shared and seeded by the application.
- Tags and collections are private to the user who created them.
- Use composite primary keys for `bookmark_tags` and `collection_bookmarks`.
- Add indexes for bookmark ownership, creation date, technology, and favorites.
- Use database transactions for operations that update multiple related records.
- Prevent users from attaching other users' tags or collections to their bookmarks.
- Define appropriate cascade deletion behavior.

Auth.js adapter-specific tables, columns, and constraints should follow the adapter's schema requirements, including verification tokens if required. Google identity is linked through the accounts table rather than trusting an email address supplied by the browser.

## 8. REST API specification

All bookmark, collection, and tag endpoints require authentication.

| Method | Endpoint                                     | Purpose                     |
| ------ | -------------------------------------------- | --------------------------- |
| GET    | `/api/bookmarks`                             | List bookmarks with filters |
| POST   | `/api/bookmarks`                             | Create bookmark             |
| GET    | `/api/bookmarks/:id`                         | Retrieve bookmark           |
| PATCH  | `/api/bookmarks/:id`                         | Update bookmark             |
| DELETE | `/api/bookmarks/:id`                         | Delete bookmark             |
| GET    | `/api/collections`                           | List collections            |
| POST   | `/api/collections`                           | Create collection           |
| GET    | `/api/collections/:id`                       | Collection details          |
| PATCH  | `/api/collections/:id`                       | Rename collection           |
| DELETE | `/api/collections/:id`                       | Delete collection           |
| POST   | `/api/collections/:id/bookmarks`             | Add bookmark to collection  |
| DELETE | `/api/collections/:id/bookmarks/:bookmarkId` | Remove from collection      |
| GET    | `/api/tags`                                  | List tags                   |
| POST   | `/api/tags`                                  | Create tag                  |
| DELETE | `/api/tags/:id`                              | Delete tag                  |
| GET    | `/api/technologies`                          | List supported technologies |
| GET    | `/api/dashboard/stats`                       | Dashboard statistics        |

Google authentication routes will be handled by Auth.js under `/api/auth/*`.

```
}
```

Use consistent HTTP status codes: `401` for unauthenticated requests, `403` for forbidden operations where appropriate, `404` for unavailable resources, and `409` for conflicts.

## 9. Security and best practices

These are important because DevStash uses real Google accounts and persistent user data.

Authentication

Use Auth.js with Google OAuth, secure session cookies, server-side session checks, and no custom password system.

Authorization

Never accept `userId` from the client as proof of ownership. Derive it from the authenticated session and verify ownership in database operations.

Input validation

Use Zod, limit string lengths, reject unsafe URL schemes such as `javascript:`, and validate IDs, categories, and tag assignments.

Secrets and environment variables

Keep Google OAuth credentials, database URLs, and Auth.js secrets in server-only environment variables. Never commit `.env.local`.

Database protection

Use parameterized queries through Drizzle, appropriate foreign keys, and a least-privilege database connection.

External links

Open resources using `rel="noopener noreferrer"` and `target="_blank"`. Avoid automatically fetching arbitrary user-submitted URLs in the MVP.

For a public deployment, also add reasonable rate limiting for write operations and ensure the application never exposes another user's private bookmarks.

## 12. Vercel deployment plan

1. Create a GitHub repository and connect it to Vercel.
2. Provision Neon PostgreSQL through the Vercel Marketplace and attach it to the project.
3. Configure Drizzle using the database connection variable supplied by the integration.
4. Run database migrations through a controlled development/deployment process, not automatically on every incoming request.
5. Configure Google OAuth in Google Cloud Console, including the exact production callback URL.
6. Add environment variables in Vercel for production and development.
7. Deploy and test login, CRUD, filters, collections, and authorization.
8. Configure the production domain and update Google's OAuth redirect settings if the domain changes.

`AUTH_URL` is only needed when required by your Auth.js version or deployment configuration. We should follow the installed version's current documentation rather than adding unnecessary configuration.
